## Two roles, always

The app's runtime `DATABASE_URL` is a restricted Postgres role
(`NOSUPERUSER NOBYPASSRLS`) - RLS is silently skipped for superusers no
matter what the policies say, which is exactly the bug this project hit
while building it. Migrations run separately, over `DATABASE_MIGRATE_URL`,
using an elevated role that can actually execute DDL. See
[Self-Hosting](/docs/self-hosting#database-roles) for the exact `CREATE
ROLE` statement.

## Migration history

`packages/db/drizzle/` currently holds 42 migrations (`0000` through
`0041`), one SQL file per schema change, applied in numeric order - every
feature module in this app (Page Analyzer, Keywords, Site Audit, AI
Visibility, Local SEO, Rank Tracking, Backlinks, Clay, Publish, Social,
and more) shipped its tables this way, incrementally, rather than as one
upfront schema. `packages/db/README.md`'s own migration-history table is
the complete, current, row-by-row list - it's regenerated there as new
migrations land, so it's kept out of this page rather than copied and
left to drift. The early sequence below is representative of the pattern
every migration since has followed:

| # | What it does |
|---|---|
| 0000 | Initial schema - identity tables + core app tables |
| 0001 | RLS policies on the core tables |
| 0002 | Feature-module tables (Page Analyzer, Keywords, Site Audit, AI Visibility, Local SEO, Integrations) |
| 0003 | RLS policies on the 0002 tables, including nested-relation cases |
| 0004 | Additive INSERT-only policies for the signup flow - a brand-new org and its first membership row can't satisfy "already a member," since neither exists yet |
| 0005 | `saved_keywords` table (the Saved Keywords watchlist) + its RLS policy, same shape as `tracked_keywords`' |
| 0006 | Moves `google_connections` from project-scoped to organization-scoped (a Google OAuth grant belongs to the account, not one project) - drops `project_id`/`property_id`, adds `organization_id` + a `UNIQUE (organization_id, service)` constraint, recreates its RLS policy; adds `projects.gsc_property_id`/`ga4_property_id` for per-project property selection. Truncates `google_connections` first - no real data to preserve at this stage, called out explicitly rather than silently

The pattern continues past 0006 exactly the way you'd expect from the
four rules below: 0018 drops `saved_keywords` once it was superseded by a
caching table, 0027 drops a self-referencing FK column Query Fan-Out
never ended up populating, 0030-0033 each add one new feature's full
table set (Outreach, Clay, Publish, Social) in a single migration since
none of them have another migration's rows to bootstrap around. See
`packages/db/README.md` for the complete list and the reasoning behind
each one.

## The four rules

1. **Never edit an applied migration file.** Add a new one, even to fix a
   mistake in the last one.
2. **Prefer additive.** New tables/columns/permissive-policies can ship
   without touching what's running; dropping or tightening can't be
   undone by a later migration.
3. **Split destructive changes across two deploys** - ship the code that
   stops depending on the old shape first, remove the old shape in a
   follow-up migration.
4. **Forward-only, no down migrations.** Fix a bad migration with a new
   one. Backups are the real safety net, not automatic rollback.

## The mistake that produced migration 0004

Worth telling straight, because it's the kind of bug that's easy to
reintroduce: a new RLS policy was written and tested successfully... by
connecting as the Postgres superuser. Superusers bypass row-level security
unconditionally - the policy could have been complete nonsense and the
test would have looked identical. The actual bug (a brand-new
organization has no membership row yet, so it can't pass a
"already-a-member" check) only showed up once tested against the real
restricted app role. **Always test policy changes as the restricted role**,
not the migration role.

## Production deploys

Run migrations as a release/pre-deploy step - once, before traffic hits
the new version - not automatically inside application startup code.
Running them on every boot risks two instances (or a crash-loop) racing
the same migration concurrently. Back up the database before applying
migrations in production; there's no automatic rollback.
