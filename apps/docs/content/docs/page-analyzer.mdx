title: Page Analyzer
description: The flagship "fix-it plan" feature — real crawl, real SERP, real keyword data, real competitor sizing, and structured AI guidance
---

The Page Analyzer is the flagship feature: paste a URL and a target
keyword (optionally a location), and it crawls the page, pulls the live
top-10 SERP for that keyword, detects what kind of page it's actually
looking at, compares it against every currently-ranking competitor (sized
by how realistically beatable each one is), produces a prioritized fix-it
action list, and generates structured AI guidance on how to outrank the
competition and get surfaced in AI answer engines. No mock data anywhere
in this pipeline.

## What it does

1. Crawls the target URL for real (`fetchAndParse()`, shared with
   [Site Audit](/docs/site-audit)) and, in parallel, pulls the real live
   top-10 Google SERP for the target keyword plus real keyword metrics for
   it.
2. Crawls every one of those real top-10 competitor URLs too, the same
   way, so every comparison below is page-vs-page on real data.
3. Runs rule-based page-type detection (homepage/product/category/
   article/standard) against the target page.
4. Sizes up to 6 unique competitor domains (plus the target's own domain)
   by real domain authority/traffic, banding each as smaller/similar/
   bigger/much-bigger than the target - "how beatable."
5. Derives a rule-based fix-it plan directly from the real crawl + Core Web
   Vitals data.
6. Generates structured AI guidance (ranking recommendations, AI-visibility
   recommendations, candidate keyword opportunities enriched with real
   DataForSEO metrics, and suggested AI-answer-engine prompts) grounded in
   all of the above - including which competitors are actually realistic
   to outrank.
7. Persists the full report so it can be revisited, re-run, or exported.

## Real data sources

| Signal | Source |
|---|---|
| On-page crawl (title, meta description, H1s, word count, images/alt text, internal/external links, canonical, noindex, real HTTP status/redirects) | `fetchAndParse()` in `@rosterseo/crawler` - real `fetch()` + `cheerio` parse, shared with [Site Audit](/docs/site-audit) so both features agree on what "missing alt text" etc. mean |
| Page type (homepage/product/category/article/standard) | `detectPageType()` in `@rosterseo/crawler` - rule-based, never an AI guess (see below) |
| On-page product data (price, currency, rating, review count, availability, brand) | `ProductJsonLd`, parsed from the page's own `schema.org/Product` JSON-LD by `fetchAndParse()` - present for the target and any competitor whose page declares one |
| Core Web Vitals (LCP/CLS/INP) | Real Google PageSpeed Insights (`fetchPageSpeedMetrics`, `@rosterseo/google/pagespeed`) - target page only, not the 10 competitors, to keep report latency bounded (a real Lighthouse run takes 10-20s) |
| Top-10 SERP competitors | Real DataForSEO `getRealSerpResults()` (`POST /v3/serp/google/organic/live/advanced`) |
| Keyword volume, difficulty, CPC, 12-month trend, search intent | Real DataForSEO `getRealKeywordMetrics()` (`POST /v3/dataforseo_labs/google/keyword_overview/live`) |
| Competitor domain authority / traffic / "how beatable" | Real DataForSEO domain + backlinks lookups via `resolveDomainSnapshot()` (`apps/web/lib/domain-snapshot.ts`), the same 7-day cache the [Competitors](/docs/competitors) page reads and writes |
| Search Console / Analytics traffic for the target page | Real GSC/GA4 calls, last 28 days, when the project has those connected |
| Merchant Center performance for the target product | Real Google Merchant API cross-reference, when the page is a product page and Merchant Center is connected |
| Ranking guidance, AI-visibility guidance, keyword opportunities, suggested AI prompts | Real, structured LLM call via `generatePageAnalysisAi()` in `@rosterseo/ai-visibility` (see below) |

Both DataForSEO functions used here (`getRealSerpResults`, `getRealKeywordMetrics`,
in `@rosterseo/dataforseo`) return an honest empty/`null` result - never
fabricated data - when `DATAFORSEO_LOGIN`/`DATAFORSEO_PASSWORD` aren't
configured or a real call fails: a `null` SERP result becomes an empty
competitor set (never invented `competitor-###.com` domains), and a
`null` keyword-metrics result renders as an explicit "data not found"
state rather than a zeroed-out metric. Neither function has a mock
fallback - this is the convention across the whole `@rosterseo/dataforseo`
package, not something specific to Page Analyzer.

### DataForSEO location handling

The form's "Location" field is freeform text (e.g. "United States"), and
`resolveLocationCode()` (`packages/dataforseo/src/client.ts`) resolves it
to a real numeric `location_code` via DataForSEO's actual country list
(`listLocationCountries()`, cached in-memory) - exact match first, then a
loose substring match (so "London, UK" or "New York, USA" still resolve),
with a small alias table (`usa`/`us` → United States, `uk` → United
Kingdom, `uae` → United Arab Emirates) layered on top. Only falls back to
the US default (`2840`) when nothing real matches at all, including when
DataForSEO isn't configured or the lookup itself fails - not a small
hardcoded country list silently swallowing anything unrecognized.

## Real, rule-based page-type detection

`detectPageType()` (`packages/crawler/src/detect-page-type.ts`) classifies
the target page as `homepage` / `product` / `category` / `article` /
`standard` - deterministic and transparent, never an AI guess. Every
result records which real signal decided it, in priority order:

1. **JSON-LD `@type`** (high confidence) - `Product` → product;
   `CollectionPage`/`ItemList`/`OfferCatalog` → category;
   `Article`/`BlogPosting`/`NewsArticle`/`TechArticle` → article.
2. **URL path heuristics** (medium confidence) - root path → homepage;
   `/products?/`, `/p/` → product; `/collections?/`, `/categor(y|ies)/`,
   `/shop/` → category; `/blog/`, `/articles?/`, `/news/` → article.
3. **Content heuristics** (low confidence, last resort) - price-like
   tokens plus many links suggests a category/listing page; a single
   price-like token on a short page suggests a product; long-form content
   with no product/category signal suggests an article.
4. Falls through to `standard` if nothing matched.

The detected type and its confidence/reasons are shown as a tooltip on the
report header's page-type badge (`PageTypeBadge`,
`apps/web/components/page-analyzer/page-type-badge.tsx`), drive whether
the Product snapshot panel renders (below), and are fed into the AI
guidance prompt so recommendations are tailored to what the page actually
is (product pricing/reviews vs. article content depth vs. category
structure) instead of generic advice.

## Product pages: real on-page + Merchant Center data

When a page (target or any SERP competitor) declares a `schema.org/Product`
node in its JSON-LD, `fetchAndParse()` parses it into a `ProductJsonLd`
(name, price, currency, availability, rating, review count, brand) - real
fields only, `null` for anything the page's own markup doesn't declare,
never estimated.

The report's Overview tab renders a **Product snapshot**
(`apps/web/components/page-analyzer/product-snapshot.tsx`) whenever the
detected page type is `product`: a side-by-side table of the target's own
product data against up to 3 competitors that also declare one. When the
target page's product name matches a product in a connected Google
Merchant Center account, the same panel also shows real Merchant Center
performance for it (clicks, impressions, CTR, conversions, last 28 days)
via `getMerchantProductPerformanceForProduct()`
(`packages/google/src/merchant-center.ts`) - matched by the page's own
declared product name against Merchant Center's Reports API, since that's
the only real link available between "the page just crawled" and "a row
in this account's catalog." An honest "connect Merchant Center" prompt
renders instead when there's a product but no connection.

The Merchant Center integration itself targets Google's newer Merchant API
(`merchantapi.googleapis.com`), not the legacy Content API for Shopping it
originally used - the query-language calls are typed against DataForSEO's
and Google's published shapes but not yet live-tested end-to-end against a
real funded Merchant Center account.

## Competitor "how beatable" sizing

Beyond the on-page comparison, each real SERP competitor's domain gets
sized against the target's own domain authority - not just left in raw
SERP-position order:

- Up to 6 unique competitor domains (plus the target's own domain,
  unconditionally, since every band is relative to it) get a real
  DataForSEO domain-authority/traffic lookup via `resolveDomainSnapshot()`
  (`apps/web/lib/domain-snapshot.ts`) - the same `competitor_snapshot_cache`
  table and 7-day staleness window the [Competitors](/docs/competitors)
  page's own snapshot fetch reads and writes, so a lookup from either
  feature keeps the other's cache fresh.
- Each sized competitor is banded relative to the target's domain rating:
  **smaller** (lower rating than the target - a strong near-term target),
  **similar** (within 15 points - a realistic near-term target), **bigger**
  (up to 2x the target's rating - a longer-term target), or **much-bigger**
  (beyond that - unlikely to outrank near-term). A row that was never
  resolved (past the top-6 cap, or the real lookup failed) is banded
  **unknown** and rendered as "not sized" - never guessed.
- The Competitors tab (`CompetitorTable`,
  `apps/web/components/page-analyzer/competitor-table.tsx`) sorts by this
  band first (target page pinned first as the reference point, then
  beatable-to-unbeatable), SERP position only as the tiebreaker within a
  band - the point of sizing competitors is putting the realistically
  beatable ones where the user actually looks first.
- The AI guidance prompt receives the same real breakdown (domain rating,
  organic keywords, estimated monthly traffic per sized competitor) and is
  explicitly instructed to prioritize strategy around the competitors
  flagged as realistically beatable rather than giving generic advice that
  ignores which ones are actually catchable.

## AI guidance

`generatePageAnalysisAi()` (`packages/ai-visibility/src/page-analysis-ai.ts`)
is a single structured LLM call, deliberately **OpenRouter-only** (no
fallback to the direct-API providers other AI-visibility features use) -
gated on `OPENROUTER_API_KEY` via `getProvider("openrouter")`. The prompt
is built entirely from real data assembled elsewhere in the pipeline: the
crawl summary, real target-keyword usage on the page (see below), real
keyword metrics, the real competitor comparison, the real page-type
signal, and the real competitor-strength breakdown when available.

The model (`google/gemini-2.5-flash` by default, overridable via
`PAGE_ANALYZER_OPENROUTER_MODEL`) returns a zod-validated JSON object with
four parts, retried up to 3 times on failure:

- **`rankingRecommendations`** - 4-8 prioritized steps to outrank the real
  competitors for this exact keyword.
- **`aiVisibilityRecommendations`** - 4-8 prioritized steps to make the
  page more likely to be cited by AI answer engines (ChatGPT, Perplexity,
  Google AI Overviews).
- **`keywordOpportunities`** - 6-10 candidate keyword phrases the AI
  proposes based on the page's real content and competitive gaps; each
  candidate then gets a real `getRealKeywordMetrics()` lookup
  (capped at 10) and any candidate DataForSEO couldn't return real data
  for is dropped, never shown with invented volume/difficulty.
- **`suggestedPrompts`** - 4-6 realistic prompts a person might type into
  an AI assistant where this page's content should be a strong, citable
  answer, each with a one-line rationale. Each can be tracked straight into
  [AI Visibility](/docs/ai-visibility) prompt monitoring with one click.

Three distinct states are rendered honestly rather than collapsed into one
"no guidance" case: **not configured** (`OPENROUTER_API_KEY` unset -
"configure OpenRouter" prompt), **failed** (configured, but the real call
didn't succeed after retries - "re-run to try again"), and reports
generated before this structured rebuild, which still render their old
freeform-prose guidance via a legacy fallback renderer instead of crashing.

## Target keyword usage

`checkKeywordUsage()` (`apps/web/components/page-analyzer/analysis.ts`) is
a real, deterministic check of whether the target keyword actually appears
on the page - no AI involved: presence in the title, meta description, any
H1, and the URL, plus a real occurrence count and density percentage over
the page's body text. Shown as a row of chips in the On-page tab and fed
into the AI guidance prompt.

## Report contents

The report view (`PageAnalyzerReportView`,
`apps/web/components/page-analyzer/page-analyzer-report-view.tsx`) opens
with a compact header - the URL, target keyword/location, the page-type
badge, a search-volume badge, and a real "ranking #N in Google's real top
10" / "not in the top 10" banner - above four tabs:

- **Overview**: the Product snapshot (product pages only), real Search
  Console / Analytics traffic for the target page (`PageAnalyticsSnapshot`),
  an issue-count summary, and the fix-it plan.
- **On-page & content** (`CrawlSummary`): a two-tier layout - a compact
  checklist row for binary present/missing checks (title tag, meta
  description, single H1, not noindex, HTTP status) and the real
  target-keyword-usage chips, then a numeric stat grid for word count,
  images missing alt text, internal/external links, load time, Core Web
  Vitals, and keyword difficulty/CPC/intent.
- **Competitors** (`CompetitorTable`): the target page plus every real
  top-10 competitor, compared on word count, H1 count, missing alt text,
  load time, and the real "how beatable" domain-authority sizing described
  above.
- **AI guidance** (`GuidanceCard`): the four structured sections above, or
  the appropriate not-configured/failed/legacy state.

**Fix-it plan** (`FixItList`): findings derived directly from the real
crawl output - broken/failed fetch, noindex, canonical mismatches,
redirects, missing title/meta description, missing or duplicate H1s, thin
content or a content-depth gap vs. the competitor average, images missing
alt text, slow load time, Core Web Vitals over Google's "good" thresholds,
and low internal-link counts - each tagged with an impact (High/Medium/Low)
and a category (Technical/Content/Structure/Indexability), sorted by
impact.

**Export/actions bar** (`ReportExportBar`): re-run the analysis, submit
the URL to Bing/Yandex/Seznam/Naver via IndexNow (the same route
[Site Audit](/docs/site-audit)'s "Notify search engines" action uses, just
scoped to this one URL), a link to Google Search Console's URL Inspection
tool when Search Console is connected (Google has no programmatic
"request indexing" API for arbitrary sites, so this links to the real tool
rather than faking automation Google doesn't offer), "Copy as Markdown"
(including traffic, product data, keyword usage, and AI guidance in the
export), and "Download PDF" (the browser print dialog against a
print-only stylesheet).

Rule definitions and orchestration live in
`apps/web/components/page-analyzer/analysis.ts`
(`buildPageAnalyzerResult()`), shared by the page and the API route so the
rule set can never drift between them.

## Database

`pageAnalyzerReports` (`packages/db/src/app-schema.ts`, table
`page_analyzer_reports`), RLS-protected like every tenant table:

| Column | Notes |
|---|---|
| `id` | UUID primary key |
| `projectId` | FK to `projects`, cascade delete |
| `url` | The page that was analyzed |
| `targetKeyword` | The keyword the page is being analyzed against |
| `targetLocation` | Optional |
| `status` | `pending` \| `running` \| `complete` \| `failed` |
| `result` | JSONB - the full `PageAnalyzerResult` (crawl, page type, Core Web Vitals, SERP results, keyword metrics, comparison rows with domain sizing, findings, keyword usage, AI suggestions, GSC/GA4/Merchant metrics), once complete |
| `createdAt` | Timestamp |

No migration was needed for the richer report shape - it's all inside the
existing `result` JSONB column. Older reports simply have fewer fields
populated (`pageType`, `aiSuggestions`, etc. are all optional in the type),
and the UI renders an honest "unknown"/empty state for whichever ones a
given historical report predates, rather than guessing retroactively.

## API

`apps/web/app/api/projects/[projectId]/page-analyzer/`, both route files
wrapped in `withAuth` and scoped with `requireProjectAccess` +
`withUserContext`.

### `POST /api/projects/:projectId/page-analyzer`

Body:

```json
{ "url": "https://example.com/page", "targetKeyword": "best running shoes", "targetLocation": "United States" }
```

`targetLocation` is optional. Inserts a `pageAnalyzerReports` row with
`status: "running"` first and responds immediately with it, then resolves
the project's real GSC/GA4/Merchant Center access tokens (when connected)
and runs the full real pipeline in the background of the same long-lived
Node process, updating the row to `complete` (with `result` populated) or
`failed` when it finishes. This is in-process fire-and-forget, not a
durable queue - a restart of this process mid-run leaves the row stuck
"running"; the client's own report view treats a report still "running"
several minutes after creation as an honest "this looks stuck" state
rather than pretending it's still normal.

Returns `201` with `{ "report": <row> }`, or `400`/`404`/`401`/`500` with
`{ "error": string }`.

### `GET /api/projects/:projectId/page-analyzer`

Returns `{ "reports": <row[]> }` for the project, most recent first, for
the history table on the main Page Analyzer page.

### `GET /api/projects/:projectId/page-analyzer/[reportId]`

Returns `{ "report": <row> }` for one report - backs the shareable
`/page-analyzer?reportId=...` report view, including polling it every 3
seconds while `status` is `"running"`.

## UI

`apps/web/app/(dashboard)/page-analyzer/page.tsx` is an async server
component (`getCurrentProject()`, matching every other page's pattern)
that renders either `PageAnalyzerWorkspace` (no `reportId` in the URL) or
`PageAnalyzerReportView` (`reportId` present), both in
`apps/web/components/page-analyzer/`:

- **`PageAnalyzerWorkspace`**: the analyze form (`AnalyzerForm` - URL,
  target keyword, optional location) and a **history table** below it
  listing past reports for the project (date, page, target keyword, page
  type badge, status, "View report" link) - each loading its saved
  `result` back into the report view instead of re-running the analysis.
- **`PageAnalyzerReportView`**: the report itself, described in full under
  "Report contents" above - header, four tabs, export/actions bar.

## History: the architecture gap this rebuild fixed

Before an earlier rebuild, the page you clicked "Analyze" on called a
Server Action (`app/(dashboard)/page-analyzer/actions.ts`) that ran the
pipeline directly - **no auth, no project scoping, no DB persistence**.
The correctly-built `POST /api/projects/:projectId/page-analyzer` route
existed the whole time but the page never called it, so every report was
silently un-tenant-scoped and lost on refresh. That was fixed by routing
the page through the real API route (`PageAnalyzerWorkspace`) and deleting
the Server Action - the persistence, history, and auth described above all
depend on that fix still holding.
