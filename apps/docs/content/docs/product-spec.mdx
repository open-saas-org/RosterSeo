## 1. Vision

A subscription SEO platform for solo SEOs and freelancers that goes beyond keyword/rank tracking: for any page, it crawls it, pulls the live SERP and top competitors, diffs the gaps, and hands back a prioritized, AI-written action plan to get that page ranking. It also tracks whether the brand shows up in AI answer engines (ChatGPT, Gemini, Perplexity, Google AI Overviews), so one subscription covers both traditional Google SEO and the emerging "GEO" (generative engine optimization) need. Data is accessible through the dashboard and, for power users, through an MCP server their own AI tools can query directly.

## 2. Target User

**Primary ICP: solo SEOs and freelance consultants** managing multiple client or personal sites, price-sensitive, want one tool instead of stitching together Semrush + a GEO tracker + a local rank checker. Not agencies (no white-label/sub-accounts needed for v1, per your answer) — each account is one user working across their own projects.

## 3. Positioning / Wedge

The flagship feature is **#8, the page analyzer** — most competitors (Semrush, Ahrefs, SE Ranking) are dashboard-first and leave the "so what do I actually do" step to the human. This product's core loop is: paste a URL and target keyword → get a crawled audit + live SERP/competitor gap analysis + an AI-generated, prioritized fix-it plan. Bundling that with AI-search visibility tracking (a feature most SEO incumbents don't have, and most GEO-only tools like Peec AI/Profound don't pair with classic SEO) is the secondary wedge.

Be aware: you're a **reseller of DataForSEO's index**, same as most of the mid-market competition. The moat is the AI synthesis quality and the combined SEO+GEO scope, not proprietary data.

## 4. Core User Journey

1. Sign up → create first project (enter domain, target market/location, primary competitors).
2. Land on project dashboard: tracked keyword rankings, site health score, AI-visibility score — the three headline numbers.
3. Run the **page analyzer** on a specific URL + keyword → get the fix-it report (this is the "aha moment," should be usable within minutes of signup, ideally in a free trial before payment).
4. Add more keywords to the research/tracking suite, run a full-site crawl, check local pack position if relevant, check AI-search visibility.
5. Return weekly/monthly to see trend changes and new AI-generated recommendations as data updates.
6. (Power users) generate an API key, point their own AI tool at the MCP server to pull project data programmatically.

## 5. Feature Requirements

All of the following are targeted for v1 per your scope answer — see Section 8 for the phased build sequence, since building all of this literally simultaneously in one sprint isn't realistic solo.

### 5.1 Page Analyzer (flagship — #8)
- Input: URL + target keyword (+ optional target location).
- Crawl the page (on-page SEO elements: title, meta, headings, content, internal links, schema, Core Web Vitals/PageSpeed).
- Pull live SERP for the keyword; identify top 5–10 ranking competitor pages.
- Crawl/diff those competitor pages against the target (content depth, structure, missing subtopics, backlink gap at a summary level).
- LLM-generated output: prioritized action list (technical fixes, content gaps, structural changes), written in plain language, ranked by expected impact.
- Output should be exportable (PDF/copyable) since it's the sellable "report" moment.

### 5.2 Keyword Research Suite (#3)
- Search volume, keyword ideas/suggestions, related & question keywords, trend data, a computed difficulty score.
- Save keywords to a project's tracked list (rank tracker).

### 5.3 Competitor Research (#4)
- Domain overview for any competitor domain: traffic estimate, top keywords, top pages.
- Backlink profile summary (with an honest in-product note that the index is not as deep as Ahrefs').
- Content/keyword gap: keywords competitors rank for that the project doesn't.

### 5.4 Full Site Crawler/Audit (#7)
- Crawl an entire domain (via DataForSEO On-Page API for v1), surface technical issues: broken links, missing meta, duplicate content, redirect chains, indexability, Core Web Vitals.
- Issue list prioritized by severity, trackable over time (re-crawl and diff).

### 5.5 Local SEO (#5)
- Local/map-pack SERP checking for a keyword at a given location.
- Geo-grid rank visualization (rank at multiple points around a service area) — **flag to user in-product that this is credit-intensive**, gate behind higher tiers or explicit credit spend.
- Google Business Profile data (Q&A, reviews) where available via the data source.

### 5.6 GSC + GA4 + Analytics Integration (#6)
- OAuth connect flow for Google Search Console and GA4 per project — each customer logs into their own Google account and grants your app access to their own properties. There's no bulk/admin access option; it's a one-time per-user consent flow, standard and well-documented.
- Pull real impressions/clicks/CTR/position (GSC) and traffic/conversions (GA4) into the project dashboard, so the AI recommendations can eventually be informed by real performance, not just estimated SERP data.
- **Good news**: `webmasters.readonly` and `analytics.readonly` are classified by Google as *sensitive* scopes, not *restricted*. That means no paid CASA third-party security audit (audits are only required for restricted scopes like broad Drive/Gmail access). Verification is Google's free review process — you submit a privacy policy, a homepage, scope justification, and a demo video of the actual OAuth flow; typical turnaround is roughly a week to a few weeks, sometimes longer with revision cycles.
- **While in "Testing" publish status you can onboard up to 100 test users with zero verification** — enough to build and beta-test the whole feature before you ever submit for review.
- **Real limits to design around**:
  - GSC Search Analytics API: 25,000 rows per request, 50,000 rows/day per site per search type, plus per-project QPS/QPM/QPD quotas — large sites need pagination (`startRow`), and very high-traffic sites can hit the daily row cap.
  - GSC data has a ~2-3 day reporting lag and only ~16 months of history — set expectations in the UI, don't imply real-time.
  - GA4 Data API: 25,000 "tokens"/day and 1,250 tokens/hour *per property* (i.e., per customer, not pooled across your whole user base — good for a multi-tenant app), 10 concurrent requests. A single dashboard load can burn ~10 tokens, so **cache aggressively and refresh on a schedule, not on every page view**, or active users will hit hourly limits.
  - Some customers won't have GA4 configured at all (still on old Universal Analytics or nothing) — plan for a "not connected" state, not just success/failure.
  - Refresh tokens can be revoked by the customer at any time from their Google account — handle re-auth gracefully, don't just fail silently.
- **How this scales in practice**: sync incrementally (pull yesterday's new data once per site per day and store it, don't re-fetch full history on every dashboard load) and the row/token caps above comfortably cover a solo-SEO/freelancer customer base. For the rare oversized customer site, both GSC (Bulk Data Export) and GA4 (BigQuery Export) offer a native, unlimited-rows export straight to BigQuery — the officially sanctioned path enterprise tools use instead of the capped REST APIs. Treat this as a phase-2 escape hatch, not a v1 requirement. Quota increases on the standard API are also a normal, grantable request if usage ever gets close to the ceiling.

### 5.7 AI-Search / LLM Brand Visibility (#10)
- Define tracked prompts per project (e.g. "best [category] in [location]", "[brand] vs [competitor]").
- Run prompts against multiple LLM providers (OpenAI, Anthropic, Google, Perplexity), multiple samples per prompt for stability.
- Parse responses for brand/domain mentions, position/rank within the answer, sentiment, and competitor mentions.
- Surface as a visibility %, trend over time, and per-prompt breakdown.

### 5.8 MCP Server (#1)
- One MCP server exposing read tools per project: get_rankings, get_keywords, get_site_audit, get_brand_visibility, get_competitors, etc.
- API keys scoped to a single project; rate-limited; revocable from account settings.
- Documented so users can point Claude/ChatGPT/other agent tools at their own project data.

### 5.10 Shopify Connect & Auto-Publish Agent (new — e-commerce wedge)
- Store connection: v1 uses a **custom app / manual access token** flow (merchant generates a token from their own Shopify admin, pastes it in) — no OAuth, no Shopify app review, works immediately. A full public app with a "Connect to Shopify" OAuth button is a phase-2 polish item, since even unlisted public-app distribution requires a Shopify review cycle (GDPR mandatory webhooks, security requirements).
- Built on the **GraphQL Admin API** (mandatory for new apps since April 2025 — REST is legacy). Bulk operations run as queued background jobs (Trigger.dev) to respect Shopify's cost-based rate limits, not as one big synchronous write.
- Scope: products (title tag / meta description / image alt text), collections (incl. FAQ content), blog posts, and redirects. Verify exact current Shopify scope names at implementation time — they get renamed periodically.
- **Agent write-back**, layered onto the page analyzer (5.1): when a fix-it plan flags an issue on a Shopify-backed page, it offers "Apply via agent."
  - Default mode: review queue with a before/after diff and one-click approve — this is writing to a live storefront, so human-in-the-loop by default.
  - Optional "trusted auto-apply" toggle, scoped to low-risk fields only (meta description, alt text), for users who opt in after seeing approvals go well.
  - Hard rule regardless of mode: any handle/URL change automatically creates a redirect from old → new. Never a silent break of an indexed/linked URL.
  - Every agent-applied change is logged with a before/after snapshot, for trust and one-click undo.
- Positioning note: this is a strong wedge specifically for the subset of your ICP doing Shopify/e-commerce SEO — worth considering as a named specialization, not just a generic integration.

### 5.9 Multi-Tenant SaaS Core (#9)
- Auth (signup/login, password + OAuth login options).
- Multi-project support per account (each project = one domain/brand).
- Billing (Stripe), subscription tiers with usage caps, in-app credit/usage meter so users can see what they're spending before they run an expensive action (crawl, geo-grid, LLM-visibility check).

## 6. Non-Functional Requirements

- **Tenant isolation**: every query scoped by project_id/account_id; enforced at the database layer (Postgres row-level security), not just in application code.
- **Cost control**: every credit-consuming action (crawl, geo-grid pull, LLM-visibility run) shows an estimated cost/credit deduction before the user confirms, and tiers have hard usage caps.
- **Async by default**: crawls, full-site audits, and LLM-visibility runs are background jobs with status polling/notifications, not blocking requests.
- **Data freshness expectations set clearly in UI**: rankings/visibility data is not real-time; show "last updated" timestamps.

## 7. Technical Architecture (leaning low-code, per your stated comfort level)

Given limited coding background, the recommended stack minimizes infrastructure you have to operate yourself — Claude can write the application code, but the platform choices below avoid you needing to manage servers directly:

- **Frontend + app hosting**: Next.js on Vercel (managed hosting, no server ops).
- **Database + Auth + Storage**: Supabase (managed Postgres with row-level security built in, managed auth, file storage for reports/exports) — one vendor covers three of your hardest infra needs.
- **Background jobs/queue**: Supabase Edge Functions or a managed queue (e.g. Inngest/Trigger.dev) for crawl/audit/LLM-visibility jobs — avoids you having to run/manage worker servers.
- **Billing**: Stripe (Checkout + Billing) for subscriptions and usage metering.
- **SEO data**: DataForSEO API (single vendor for keywords, SERP, backlinks, on-page crawl, local/business data).
- **AI/LLM**: Claude (and other provider APIs as needed for the multi-provider AI-visibility feature) via direct API calls, using a cheap/fast model for the visibility-sampling feature to control cost, a stronger model for the page-analyzer's fix-it plan since quality there is the product's differentiator.
- **MCP server**: hosted as its own lightweight service (can live on the same Vercel/Supabase infra), using the MCP SDK.
- **Shopify**: `@shopify/shopify-api` / `@shopify/admin-api-client` against the GraphQL Admin API, custom-app token flow for v1 (Section 5.10).

This whole stack is "managed services" end to end — no servers to patch, no infra to scale manually, which fits your stated technical comfort level. I (Claude) can write essentially all of the application code; your role is mostly product decisions, testing, and content/business setup.

## 8. Cost Model & Illustrative Unit Economics

DataForSEO and LLM costs are usage-based — treat this as a variable cost you pass through in pricing, not a fixed license fee.

| Action | Rough cost driver | Notes |
|---|---|---|
| Single SERP check | ~$0.0006–0.002 per query (queue speed dependent) | Core cost behind rank tracking, keyword difficulty, page analyzer |
| Keyword data lookup | Sub-cent to a few cents per call, endpoint-dependent | Verify exact current pricing per endpoint on DataForSEO's site before finalizing tier limits |
| On-page crawl | Priced per page crawled | Full-site audits scale with site size — cap pages/crawl per tier |
| Local geo-grid check | N grid-points × keywords × SERP cost | E.g. a 5×5 grid × 10 keywords = 250 SERP calls per run — this is your most expensive per-click feature, price/gate accordingly |
| AI-visibility sample | Token cost of one LLM call (fractions of a cent with a cheap model) × samples needed for stability × number of providers tracked | A tracked prompt sampled 5× across 4 providers = 20 calls per check cycle |
| Page-analyzer fix-it plan | 1 on-page crawl + ~5–10 SERP/competitor pulls + 1 higher-quality LLM synthesis call | Your flagship feature — costs more per-run than a single keyword lookup, price it as a distinct "report" action, not unlimited-use |

**Google APIs (GSC/GA4) cost $0** — no per-call fee, no CASA audit fee (sensitive scopes only). The only "cost" is your time going through Google's free verification review.

The honest takeaway: getting to a launchable v1 costs you almost nothing in cash (well under a few hundred dollars total across the build phase) — it costs your time. There's no scenario here that requires the $60k-150k agency-build numbers from Section 4 unless you hire that work out.

**Pricing tiers (placeholder numbers to refine once real usage data exists)**:
- Starter (~$29/mo): 1–3 projects, capped keywords tracked, a handful of page-analyzer reports/mo, no local geo-grid, basic AI-visibility (fewer prompts/providers).
- Pro (~$79/mo): more projects, higher keyword cap, more page-analyzer reports, local geo-grid included with a monthly cap, fuller AI-visibility tracking, GSC/GA4 connections.
- Add-on credits: for users who blow through caps (extra crawls, extra geo-grid runs, extra AI-visibility prompts) rather than forcing a tier upgrade.

## 9. Phased Roadmap (reality check on the 3–4 month timeline)

You've scoped essentially every feature into v1. Solo, with AI-assisted coding and limited hands-on-code background, 3–4 months is workable **if features ship in sequence, not simultaneously** — each phase below is a shippable, demoable milestone, not a big-bang launch at month 4.

**Month 1 — Core + flagship feature**
Auth, multi-project accounts, billing skeleton, project dashboard shell, keyword research suite, and the page analyzer (the wedge feature) working end-to-end on DataForSEO data. This alone is enough to start showing to potential early users.

**Month 2 — Breadth: crawler + competitors**
Full-site crawler/audit, competitor research suite, credit-metering UI wired up properly (needed before you open paid signups).

**Month 3 — Google integration + local**
Kick off Google OAuth verification at the *start* of this phase (or earlier — it can run in parallel with Month 1–2 work since it's mostly a paperwork/review process, not dev time). Build GSC/GA4 integration and local SEO/geo-grid tracking.

**Month 4 — AI-search visibility + MCP + polish**
LLM brand-visibility tracking, MCP server, billing/tier polish, onboarding flow, launch prep.

**Phase 2 (post-launch, first priority) — Shopify Connect & Auto-Publish Agent**
Custom-app token connection, agent write-back on the page analyzer, review-queue UX, redirect safety net. Positioned as the e-commerce/Shopify specialization wedge once the core product is validated. Move into v1 only if you're willing to extend the timeline — see open item below.

This sequencing gets you to "all features live" around the 3–4 month mark while giving you something demoable/sellable as early as month 1, rather than betting the whole timeline on everything landing at once.

## 10. Risks & Mitigations

| Risk | Mitigation |
|---|---|
| No proprietary data moat (reselling DataForSEO) | Differentiate on AI synthesis quality (page analyzer) and SEO+GEO bundling, not raw data depth |
| Google OAuth verification delay | Start the process in month 1 regardless of feature sequencing |
| Local geo-grid & AI-visibility costs spiral with usage | Hard per-tier caps + visible credit meter before every expensive action |
| LLM answers are non-deterministic (visibility tracking noise) | Multiple samples per prompt per cycle, show confidence/variance not just a single %, be transparent in-product about methodology |
| Solo build, ambitious scope, fixed timeline | Sequence features into monthly shippable milestones (Section 9) rather than one big launch |
| Agent writing directly to a customer's live storefront gets something wrong | Review-queue default, auto-apply limited to low-risk fields only, mandatory redirect on any URL/handle change, full audit log with undo |
| Competing against well-funded incumbents | Lean hard into the ICP (solo/freelance) and the wedge (AI fix-it plan) rather than trying to out-feature Semrush generally |

## 11. Success Metrics (draft — refine once you have a business model target)

- Activation: % of signups who run a page-analyzer report within their first session.
- Conversion: trial → paid conversion rate.

- Unit economics: gross margin per tier after DataForSEO/LLM costs, monitored per-tier not just in aggregate (heavy local/GEO users could erode margin on lower tiers).
