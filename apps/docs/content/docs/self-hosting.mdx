## Local development (no Docker)

Requires Node 22.13+ (pnpm 11 itself needs it), pnpm, and a Postgres instance (local install, or a free
one from Railway/Neon/Supabase).

```bash
cp .env.example .env
pnpm install
```

Postgres needs two roles before running migrations — see
[Database roles](#database-roles) below, then:

```bash
pnpm db:migrate
pnpm dev
```

`apps/web` runs on `http://localhost:3000`, `apps/docs` on `http://localhost:3001`.
`apps/worker` (the job queue consumer) starts alongside them via the same
`pnpm dev`.

## Self-host via Docker

**Docker Compose** — app + a real local Postgres, good for trying it out:

```bash
cp .env.example .env
docker compose up --build
```

`docker/postgres-init.sql` creates the restricted app role automatically on
first container start. Migrations run automatically on container start too
(see `docker/docker-entrypoint.sh`, baked into the image's `ENTRYPOINT`) —
there's nothing to run by hand after `up`.

**Just the Dockerfile**, against a Postgres you already have (a managed
instance, another container, whatever) — this is the plain "build an image
and run it anywhere" path for a VPS, Fly.io, Render, or any other
Docker-based host that isn't Railway:

```bash
docker build -t rosterseo-web .
docker run -p 3000:3000 \
  -e DATABASE_URL="postgres://user:pass@your-postgres-host:5432/rosterseo" \
  -e BETTER_AUTH_SECRET="$(openssl rand -hex 32)" \
  -e BETTER_AUTH_URL="http://localhost:3000" \
  -e NEXT_PUBLIC_BETTER_AUTH_URL="http://localhost:3000" \
  rosterseo-web
```

Same automatic migration-on-start behavior as Compose — the image migrates
the database it's pointed at, then serves the app, every time it boots. See
`.env.example` for every other variable (DataForSEO, AI providers, OAuth,
etc.) — all optional beyond the ones above, each one just stays inert until
you set it.

## Database roles

This is the one setup step that's easy to get wrong and fails silently if
you do: **the app's runtime `DATABASE_URL` must be a non-superuser role**,
or Postgres row-level security (the tenant-isolation mechanism) is skipped
entirely — no error, it just quietly returns every tenant's rows.

```sql
CREATE ROLE rosterseo_app WITH LOGIN PASSWORD '<pick one>' NOSUPERUSER NOBYPASSRLS;
GRANT ALL PRIVILEGES ON ALL TABLES IN SCHEMA public TO rosterseo_app;
GRANT ALL PRIVILEGES ON ALL SEQUENCES IN SCHEMA public TO rosterseo_app;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT ALL ON TABLES TO rosterseo_app;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT ALL ON SEQUENCES TO rosterseo_app;
GRANT CREATE ON DATABASE rosterseo TO rosterseo_app;
```

Set `DATABASE_URL` to this restricted role, and `DATABASE_MIGRATE_URL` to
an elevated (superuser/owner) role — migrations run DDL that a restricted
role can't execute. Full detail: `packages/db/README.md` in the repo.

## Deploy on Railway

The deploy mechanics are already real and working: `railway.toml` at the
repo root tells Railway to build `Dockerfile` and, via its
`releaseCommand`, run the real Drizzle migrations
(`node packages/db/dist/migrate.mjs`) once per deploy, before traffic
switches to the new release — attach a **PostgreSQL** plugin, set the
required variables from `.env.example` (`SELF_HOSTED`,
`BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `DATAFORSEO_LOGIN`/
`DATAFORSEO_PASSWORD`, plus whichever AI-provider keys you want enabled),
and it comes up with a fully migrated schema — no manual step required.

What's *not* done yet is turning that into an actual clickable **"Deploy on
Railway" button** — that's a one-time action in Railway's own dashboard
(Project Settings → Create Template), not something a file in this repo can
produce by itself. See `docker/RAILWAY.md` for the exact steps to publish
that template.

## Two modes

- **`SELF_HOSTED=true`** — single-tenant, no billing, bring your own
  DataForSEO/LLM API keys.
- **`SELF_HOSTED=false`** — multi-tenant hosted SaaS, Stripe billing,
  per-org credit metering.

Same codebase, one env flag.
