title: Site Audit
description: Real crawler-backed technical SEO audit — same-origin link discovery, per-page issue rules, health scoring, tracked over time
---

Full Site Crawler / Audit. Crawls a project's domain for real (fetch +
HTML parsing, not mock data), derives technical SEO issues rule-by-rule
from what it actually finds, rolls them up into a 0-100 health score, and
persists the run so it can be tracked over time.

## What it does

1. Seeds the crawl frontier from the domain's homepage plus its
   `sitemap.xml` (or a custom sitemap URL), falling back to the
   `robots.txt` `Sitemap:` directive if the default 404s.
2. Crawls breadth-first in concurrency-limited waves (`apps/worker/src/features/crawler.ts`):
   fetches each page for real, parses the HTML with `cheerio`, and follows
   every same-origin `<a href>` it discovers — not just the sitemap. A basic
   `robots.txt` subset (`User-agent: *` / `Disallow`) is respected, and
   every fetched URL passes a real SSRF guard (`assertPublicHost`,
   `@seo-tool/crawler`) before the request goes out, rejecting anything
   that resolves to a private/loopback/link-local address.
3. Tracks two distinct, real counters as the crawl runs: **pages discovered**
   (the frontier size — every same-origin URL seen so far) and **pages
   crawled** (pages actually fetched). The crawl stops once `pagesCrawled`
   hits the run's configured `maxPages`.
4. Derives per-page issues from each page's real HTML via `deriveIssues()`
   (`packages/crawler/src/derive-issues.ts`) — a pure function shared
   between the full crawl (`apps/worker/src/features/audit-runner.ts`) and
   the per-page recrawl API route below, so re-checking one page after a
   fix produces exactly the issues a full re-crawl would, never a second
   copy of the rules that can drift:

   | Rule | Severity | Category |
   |---|---|---|
   | Fetch failed (DNS/timeout/network error) | Critical | Links |
   | HTTP status &ge; 400 | Critical | Links |
   | Page redirected | Info | Redirects |
   | Missing `<meta name="description">` | Critical | Meta |
   | No `<h1>` | Critical | Content |
   | Multiple `<h1>` | Warning | Content |
   | Images missing `alt` | Warning | Accessibility |
   | Load time &gt; 2500ms | Warning | Performance |
   | Body word count &lt; 300 | Info | Content |
   | `<meta name="robots" content="noindex">` | Warning | Indexability |

   Two more checks run separately, over the whole crawl rather than one
   page at a time, directly in `audit-runner.ts`:

   | Rule | Severity | Category |
   |---|---|---|
   | Poor CLS (via PageSpeed, sampled) | Warning | Core Web Vitals |
   | Duplicate `<title>` across &ge; 2 crawled pages (runs once after the crawl finishes) | Warning | Content |

5. Computes a health score: starts at 100, subtracts 15 per critical issue,
   6 per warning, 2 per info, floored at 0.
6. Surfaces the result as a health-score metric, pages-crawled / issue-count
   summary tiles, a sortable/filterable issues table, and a per-page table
   (status code, title, H1 count, word count, image count, load time).

## Configurable page limit, not a hardcoded cap

`maxPages` is a real, user-facing input (Custom Config on the audit list
page), not a hidden constant:

- Default **200**, adjustable from **10** to **5,000**.
- Persisted per-run on `site_audits.max_pages`, so a finished audit's
  progress bar and history row both show real numbers against the ceiling
  that run actually used.
- A crawl with no ceiling at all is one crawler-trap site away from running
  forever on a shared background worker — 5,000 is deliberately high
  ("enterprise-scale," not "50 and stuck") while still being a real,
  bounded stopping point. A per-page cap on stored discovered links (500)
  and a hard frontier-size cap (`maxPages × 20`, minimum 2,000) protect
  against pathological sites (e.g. infinite calendar/faceted-nav pages)
  from exhausting worker memory before `maxPages` is even reached.

## Core Web Vitals sampling

Real Lighthouse audits (`fetchPageSpeedMetrics`, Google's PageSpeed
Insights API) take several seconds per URL and are rate-limited without an
API key. Running one on every crawled page would make a 200-page audit take
hours. The worker samples the first 20 successfully-fetched pages instead —
enough to catch template-level CWV issues (most sites have a handful of
distinct page templates) without making the crawl impractically slow.

## Deep check: broken links, orphaned pages, keyword cannibalization

A separate, opt-in pass over an already-**complete** audit's crawl data —
deliberately not part of the crawl itself, since it's the only slow,
networked part of Site Audit (live external-link checks plus a real
Search Console call) and the user asked for it not to be bundled into the
main Issues tab. Triggered manually from the audit detail page
(`SiteAuditDeepCheck`, `apps/web/components/site-audit/site-audit-deep-check.tsx`)
and tracked on its own `deepCheckStatus` lifecycle
(`null` / `pending` / `running` / `complete` / `failed`) separate from the
audit's own `status`.

- **Broken links**: internal links to pages that returned an error (from
  this audit's own crawl data), plus a real, live check of up to 300
  external links (concurrency-limited, 8s timeout per link).
- **Orphaned pages**: live, non-redirected pages that no other crawled page
  links to — derived from the real link graph captured during the crawl
  (`site_audit_links`, every `sourceUrl → targetUrl` edge seen). Skipped
  with an honest warning, not run against partial data, when the crawl
  stopped early (`crawlCompleted: false`) or the link graph exceeded what
  gets stored per audit (`linkGraphComplete: false`) — both flags persisted
  on the `site_audits` row itself so the deep check (which can run long
  after the crawl finished, as its own job) knows without re-crawling.
- **Keyword cannibalization**: real Google Search Console queries (last 28
  days) where more than one page on the site shows up, pulled live via the
  project's connected GSC property — an honest "no cannibalization found,
  or Search Console isn't connected" when there's no connection, never a
  fabricated result.

## Database

Four tables (migrated, all RLS-protected — see `packages/db/src/app-schema.ts`):

- **`site_audits`** — one row per audit run: `projectId`, `status`
  (`pending` | `running` | `analyzing` | `complete` | `failed`),
  `pagesCrawled`, `pagesDiscovered`, `maxPages`, `healthScore` (0-100),
  `startedAt`, `completedAt`, plus `crawlCompleted` and
  `linkGraphComplete` (both feed the deep check's orphan-detection
  honesty check above) and `deepCheckStatus` / `deepCheckStartedAt` /
  `deepCheckCompletedAt` for the separate deep-check lifecycle.
- **`site_audit_issues`** — one row per derived issue: `auditId`,
  `severity`, `category`, `url`, `description`.
- **`site_audit_pages`** — one row per crawled page: `auditId`, `url`,
  `statusCode` (the real HTTP status, not hardcoded), `title`, `h1Count`,
  `wordCount`, `imageCount`, `loadTimeMs`, `redirectedTo`, `canonicalUrl`,
  `metaRobots`, `crawlDepth` (real BFS link-distance from the seed),
  `h2Texts`, plus a manual per-page triage pair the crawler never writes
  — `action` (`no_action` | `in_progress` | `fixed`) and `notes` — set by
  a user working through issues after a crawl.
- **`site_audit_links`** — the real link graph captured for free during the
  main crawl: one row per `sourceUrl → targetUrl` edge, with `isExternal`,
  powering the deep check's orphaned-page detection.

## The RLS bug this replaced

An earlier worker implementation used the bare `db` export instead of
`withUserContext(userId, ...)` for every read/write. Every tenant table's
`tenant_isolation` policy checks `current_setting('app.current_user_id', true)`,
which is `NULL` outside `withUserContext` — so every `UPDATE` to `site_audits`
silently affected 0 rows (no error, RLS just filtered it out), and the first
`INSERT` into `site_audit_issues` threw a real RLS violation once a page
produced any issue. The audit row got stuck at `pending`/`running` forever
with `pagesCrawled: 0` — this is why the UI appeared to hang at "0 / 50
pages" indefinitely. Separately, `site_audit_pages` had no RLS policy at
all until a later migration added one.

Fixed by threading `userId` through the `site_audit_job` payload
(`packages/jobs/src/site-audit-job.ts`) and wrapping every DB call in the
worker in `withUserContext(userId, ...)`
(`apps/worker/src/features/audit-runner.ts`). This bug class (RLS silently
no-oping outside `withUserContext`) has bitten this codebase before — see
`ARCHITECTURE.md` — the worker just hadn't been brought in line with the
route-handler convention until this was fixed.

## API

`apps/web/app/api/projects/[projectId]/site-audit/`, behind `withAuth` +
`requireProjectAccess` + `withUserContext`:

- **`POST /`** — creates a `pending` `site_audits` row and enqueues
  `site_audit_job` (`packages/jobs`) for the worker to pick up. Accepts
  `domain`, `customSitemapUrl`, and `maxPages` (clamped 10–5,000, default
  200) in the body.
- **`GET /`** — lists the project's past audits, most recent first.
- **`GET /[auditId]`** — full audit detail: the audit row plus all its
  issues and pages.
- **`DELETE /[auditId]`** — deletes the audit (cascades to its pages/issues).
  Also doubles as **cancel**: the worker checks between crawl batches
  whether its own audit row still exists, and stops crawling as soon as
  it's gone instead of continuing to write into nothing.
- **`GET /[auditId]/progress`** — lightweight polling endpoint (status,
  `pagesCrawled`, `pagesDiscovered`, `maxPages`, five most recent pages),
  polled every 1.5s by the UI while an audit is `pending`/`running`.
- **`GET /[auditId]/deep-check`** — status and results of the on-demand
  deep-check pass described above.
- **`POST /[auditId]/deep-check`** — triggers a deep-check run for a
  completed audit.
- **`GET /[auditId]/pages/[pageId]`** — one page's full detail: the page
  row, its issues, and its real inbound/outbound links from
  `site_audit_links`.
- **`POST /[auditId]/pages/[pageId]/recrawl`** — re-fetches and re-parses
  just this one page (not the whole site) and refreshes its own
  `site_audit_pages` row plus its own `deriveIssues()`-derived issues, so a
  user can confirm a fix landed without paying for a full re-crawl.
  Cross-page state (the link graph, duplicate-title detection, deep-check
  results) is untouched — those only make sense over the whole crawl.
- **`GET /[auditId]/page-metrics`** — real per-page Search Console
  (impressions/clicks/CTR/position) and GA4 (sessions/engagement rate)
  metrics for the project, last 28 days, keyed by URL path so the Pages
  table can join them onto its own crawled rows. Returns an honest "not
  connected" per source rather than fabricated numbers.

## Worker

`apps/worker/src/features/crawler.ts` — the crawl engine (`crawlSite()`):
concurrency-limited BFS, `robots.txt`-aware, same-origin-only, no DB
knowledge (pure fetch + parse, driven by callbacks).

`apps/worker/src/features/audit-runner.ts` — owns all DB access and
business logic: calls `crawlSite()`, derives per-page issues via the
shared `deriveIssues()` (`@seo-tool/crawler`), persists pages/issues/progress
after each crawled page, captures the real link graph, runs the cross-page
duplicate-title check once the crawl finishes, and computes the health
score.

`apps/worker/src/features/site-audit-deep-check-runner.ts` — the deep
check's own job: live external-link checks, orphan detection over the
stored link graph, and the real Search Console cannibalization query.

## UI

`apps/web/app/(dashboard)/site-audit/page.tsx` routes between
`SiteAuditView` (history + launch a new audit), `SiteAuditDetail` (a single
audit), `SiteAuditDeepCheck`, and `SiteAuditPageDetail`, all in
`apps/web/components/site-audit/`:

- **`SiteAuditView`** — audit history table (date, status, pages crawled /
  max pages, health score, delete), and a launch form with a Custom Config
  section (target domain, custom sitemap URL, max pages).
- **`SiteAuditDetail`** — while running: a live progress card showing real
  discovered/crawled counts against the run's `maxPages`, polled every
  1.5s, with a Cancel button. Once complete: health-score and issue-count
  KPI cards, Issues/Pages tabs (`site-audit-columns.tsx` for the issues
  table, filterable by severity), and a **"Notify search engines"** action
  (`IndexNowSubmitAction`) that submits real crawled URLs — or manually
  entered ones — to Bing/Yandex/Seznam/Naver via the project's real
  IndexNow key.
- **`SiteAuditPageDetail`** — one crawled page's own view: its real crawl
  data, its issues, its real inbound/outbound links (flagging orphan status
  and broken outbound links), and a recrawl action.
- **`SiteAuditDeepCheck`** — the deep-check results view described above:
  broken links, orphaned pages, and keyword cannibalization, each linking
  back to the relevant page's detail view.

Shared types (`IssueSeverity`, `SiteAuditIssue`) live in
`apps/web/components/site-audit/audit-engine.ts` — the actual
crawl/issue-derivation logic lives in `@seo-tool/crawler` (`deriveIssues()`)
and the worker, reused by the per-page recrawl API route too, so there's
one real implementation rather than copies that could drift apart.
